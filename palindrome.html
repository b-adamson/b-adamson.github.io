palindrome: a computer that can’t forget

October 2026 · OxHack, joint 2nd place

Every computer you have used forgets. When it runs x = 5, whatever x held before is gone. That is why you can’t just run a program backwards, and why a debugger that lets you step back has to keep a diary of everything the program overwrote.

At OxHack 2026 (24 hours, theme: time, team of four) we built a machine where no instruction is allowed to throw anything away. Every step has an exact inverse, so going back in time doesn’t mean reading a diary, it means running the inverses. We came joint second. You can try it in the browser (pick Pong, lose, then step back), the code is on GitHub, and the hackathon submission is on Devpost.

Like most hackathon code now, most of this was written with Claude Code. My job was the core of the machine: the instruction set, the virtual machine that runs it, and the debugger that steps backwards. The rule for the ISA is that every instruction has to be a bijection on the whole machine state. Addition becomes add-in-place, which subtraction undoes. A copy becomes an XOR into a register that’s already zero. Nothing is ever simply overwritten.

instructioneffectinverse
ADD ra, rbra += rbra -= rb
XOR ra, rbra ^= rbitself
ROLI ra, krotate left by krotate left by 32 − k
CSWAP rc, ra, rbif rc ≠ 0, swap ra and rbitself

Four of the 19 instructions. The awkward cases are the ones that look harmless: ADD r1, r1 doubles r1 and loses its top bit, so the machine faults if the two operands are the same register. CSWAP is a Fredkin gate, a conditional that loses no information.

In the VM, undoing a data instruction is the same code run with a flag flipped. Every case in the switch knows its own inverse:

case Op::ADD:
case Op::SUB: {
    if (a == b) return fault("ADD/SUB operands must differ");
    const bool add = (i.op == Op::ADD) != inverse;
    regs_[a] = add ? regs_[a] + regs_[b] : regs_[a] - regs_[b];
    break;
}
case Op::ROLI: {
    const uint32_t k = i.imm18 & 31;
    regs_[a] = rotl(regs_[a], inverse ? (32 - k) & 31 : k);
    break;
}

From reversible_vm.cpp. ADD run backwards is SUB, and SUB run backwards is ADD, so one line covers all four cases.

Data is the easy half. The hard part is control flow. Going forwards, the program counter always knows where to go next. Going backwards, it has to work out where it came from, and a normal jump forgets that. If two paths lead to the same line, which one did you take?

The fix is a landing instruction, LND. Every jump has to land on one, and the LND carries a condition that is true exactly when you arrived by the jump rather than by falling through from the line above. Stepping back, the VM checks the condition at the landing. If it holds, it returns to the jump. If not, it steps to the previous line. It works out the past from the present state alone, with no log.

if (i.op == Op::LND && cond(i)) {   // we arrived by the jump from i.target
    const Instr br = decode(prog_.code[i.target]);
    if (br.op != Op::BR || br.target != q)
        return fault("LND source is not a BR to this landing");
    pc_ = i.target;
    return RVM_OK;
}

Undoing a jump. Calls work the same way: a PROC marks each procedure’s entry, and the return address is XORed onto the stack and XORed off again, leaving the slot zero.

If you can never throw anything away, temporaries pile up. Bennett’s trick from 1973 handles this: compute what you need into a scratch register, copy or use the result, then run the computation backwards to clear the scratch register again. The assembler does this for you. You write the compute block once, and it writes the undo:

.compute                ; r2 = rotl(r1, 3) + 7
xor    r2, r1
roli   r2, 3
addi   r2, 7
.use
xst    r2, [r0+0x100]   ; memory[0x100] ^= 47
.uncompute              ; assembler writes the inverse; r2 = 0 again

From examples/asm/bennett.s. Whatever a program can’t uncompute stays behind as “garbage”. A sort, for example, has to remember which way it sorted.

On top of the assembler there’s a small language, rev, in the family of Janus (1982). It looks almost normal, but every statement has an inverse. Assignment only comes as +=, -=, ^= or a swap, and a loop has an entry condition as well as an exit condition, so it can be run backwards too. The compiler uses Bennett’s trick on every expression.

proc step {
  a += b;
  a <=> b;
}

main {
  from (i == 0) loop {
    call step;
    i += 1;
  } until (i == n);
}

Reversible Fibonacci. After n steps (a, b) holds (fib(n), fib(n+1)). Run it backwards and it turns them back into (0, 1).

To check the machine, there are two engines behind the same interface. One runs normally and keeps a full log of every change, so it is easy to trust. The reversible one keeps nothing. Tests run both side by side and compare their state after every step, including random jumps forwards and backwards in time. When we broke the inverse of an instruction on purpose, the tests caught it.

The debugger sits on top of the reversible engine. Because stepping back is free, it can answer “which line last wrote this variable?” by running time backwards until the value changes, while holding 0 bytes of history.

Undoing isn’t free though, the cost just moves. You can’t overwrite, so programs have to copy, compute, then uncompute their temporaries. We wrote conventional versions of the same programs and measured both:

pong, rewindingmemory per frame
naive log19,145 bytes
bit-packed log126 bytes
checkpoint every 10k steps15 bytes
reversible8 bytes (just the input)

The reversible machine runs 3.0 to 3.3 times as many instructions as the conventional versions. Checkpointing is roughly level on memory and faster at jumping a long way back. Pong has a tiny state, which suits checkpointing.

So it’s a trade, not a free lunch. None of the idea is new either: Landauer and Bennett worked out the theory in the 1960s and 70s, and languages like Janus have existed since the 1980s. What we did was build the whole thing end to end and measure it honestly.
