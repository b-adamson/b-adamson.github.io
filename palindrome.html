palindrome: a computer that can’t forget

October 2026 · OxHack, joint 2nd place

Every computer you have used forgets. When it runs x = 5, whatever x held before is gone. That is why you can’t just run a program backwards, and why a debugger that lets you step back has to keep a diary of everything the program overwrote.

At OxHack 2026 (24 hours, theme: time, team of four) we built a machine where no instruction is allowed to throw anything away. Every step has an exact inverse, so going back in time doesn’t mean reading a diary, it means running the inverses. We came joint second. You can try it in the browser (pick Pong, lose, then step back) and the code is on GitHub.

My part was the core: the instruction set, the virtual machine that runs it, and the debugger that steps backwards. The rule for the ISA is that every instruction has to be a bijection on the whole machine state. Addition becomes add-in-place, which subtraction undoes. A copy becomes an XOR into a register that’s already zero. Nothing is ever simply overwritten.

instructioneffectinverse
ADD ra, rbra += rbra -= rb
XOR ra, rbra ^= rbitself
ROLI ra, krotate left by krotate left by 32 − k
CSWAP rc, ra, rbif rc ≠ 0, swap ra and rbitself

Four of the 19 instructions. The awkward cases are the ones that look harmless: ADD r1, r1 doubles r1 and loses its top bit, so the machine faults if the two operands are the same register. CSWAP is a Fredkin gate, the conditional that makes branching possible without losing information.

To check the machine, there are two engines behind the same interface. One runs normally and keeps a full log of every change, so it is easy to trust. The reversible one keeps nothing. Tests run both side by side and compare their state after every step, including random jumps forwards and backwards in time. When we broke the inverse of an instruction on purpose, the tests caught it.

The debugger sits on top of the reversible engine. Because stepping back is free, it can answer “which line last wrote this variable?” by running time backwards until the value changes, while holding 0 bytes of history.

Undoing isn’t free though, the cost just moves. You can’t overwrite, so programs have to copy, compute, then uncompute their temporaries. We wrote conventional versions of the same programs and measured both:

pong, rewindingmemory per frame
naive log19,145 bytes
bit-packed log126 bytes
checkpoint every 10k steps15 bytes
reversible8 bytes (just the input)

The reversible machine runs 3.0 to 3.3 times as many instructions as the conventional versions. Checkpointing is roughly level on memory and faster at jumping a long way back. Pong has a tiny state, which suits checkpointing.

So it’s a trade, not a free lunch. None of the idea is new either: Landauer and Bennett worked out the theory decades ago, and languages like Janus have existed since the 1980s. What we did was build the whole thing end to end and measure it honestly.
